## 2. 按优先级实施

### P0：① 建立 STOP 与发送提交的共同边界

**范围：** 核验表中的 service、engine、outbox，以及 app、[operations.py](<D:/SMS Reception Assistant/reception/operations.py>)；复用现有记录与审计结构。

- 将 STOP 入库、撤销发送能力、抑制记录、取消尚未提交队列、事件/历史/审计及 inbox 完成状态合为一个事务。提取由调用方持有事务的内部处理函数，避免嵌套 SQLite 连接上下文提前提交。
- 建立按联系人共享的发送/撤销屏障，固定顺序为：联系人屏障 → Engine 锁 → 短数据库事务。所有 STOP 入口、重启恢复和实际发送调用遵守此边界。
- 网络发送期间保留联系人屏障，释放 Engine 锁和数据库事务，让早到状态回调能够处理。STOP 可以取消已领取但尚未开始提交的任务；已在途、已接受或 `uncertain` 的任务保留真实状态。
- 服务启动与离线维护共用规范数据库路径及 Linux 排他锁；拒绝数据库/锁文件符号链接和硬链接别名。在线一致备份继续保留，恢复与维护仍要求排他访问。
- 关闭时停止新任务，等待 worker 和已受理请求排空后再关闭数据库、释放实例锁。超时明确报告未完成关闭，不能将仍运行的线程当作已停止。

**回归与验收：** 用线程事件精确控制两个旧空隙；STOP 撤销事务先提交时，该号码之后零新发送调用。覆盖自动/人工队列、已领取任务、429 重排、重复 STOP、早到回调、超时、崩溃恢复、慢请求关闭，以及 Linux 第二实例和并发维护被拒绝。

**风险与承诺边界：** 已开始的发送尝试可能使该号码 STOP 接受等待；等待超时返回可重试错误，不能返回撤销成功。以撤销事务成功提交为退订接受边界，不把最后门禁或 attempt 入库当作运营商接受。**不承诺撤回已在途或运营商已接受的短信；未知结果不自动重发。**

### P1：⑥ 修复代理限流及认证输入处理

**范围：** app、auth、config、[Nginx 模板](<D:/SMS Reception Assistant/deploy/nginx.conf.example>)、[配置示例](<D:/SMS Reception Assistant/.env.example>)。

- 新增 `TRUSTED_PROXY_CIDRS`，默认空。未受信连接只使用连接端 IP；受信代理路径只接受一个合法、规范化的客户端 IP，缺失、重复或畸形转发值拒绝处理。
- 支持的模板继续覆盖客户端提供的转发头；不增加代理链支持，也不使用转发头重建 Twilio 验签地址。信任范围由明确配置限定，符合 [Nginx 官方信任代理机制](https://nginx.org/en/docs/http/ngx_http_realip_module.html)。
- 保留每客户端五次失败/五分钟规则，清理过期限流记录。Cookie 解析捕获 `CookieError` 等输入异常，畸形输入按未认证处理；这是 [Python 官方 Cookie 文档](https://docs.python.org/3.12/library/http.cookies.html) 明确要求处理的异常。
- 启动时严格解析 scrypt 六段格式、固定参数、合法 Base64、16 字节盐和 64 字节摘要；现有生成器产出的有效 hash 保持兼容。错误配置启动即失败，错误输入不泄露 hash 或密码。

**回归与验收：** 两个代理后客户端限流独立；伪造转发头不能换桶；覆盖未受信来源、IPv4/IPv6、重复/畸形头、异常 Cookie、错误 hash 和有效登录。异常输入不得造成断连或服务器异常，CSRF、Host、Origin、退出和会话过期检查继续通过。

**风险：** 受信代理配置过宽会允许身份伪造；默认不信任，模板仅支持明确的单跳代理。

### P1：② 建立可审计的服务回复依据

**范围：** engine、service、outbox、app、[前端](<D:/SMS Reception Assistant/web/app.js>) 和增量迁移。

- 联系人增加权限来源事件及依据类型；outbox 快照保存来源、依据和截止。默认窗口仍为 24 小时、配置上限仍为 24 小时，均从核验后的 Twilio 资源时间起算。
- `/api/human-reply` 增加可选 `reply_to_event_id` 和 `confirm_service_inquiry:true`。未知咨询须人工明确确认；同事务核验联系人、客户号码、持久化核验来源、截止和当前限制，再记录确认审计并入队。旧请求格式仅在已有可靠权限时继续有效。
- UI 显示来源短信和截止，提供明确确认控件。接管、恢复、审核或回复均不自行续期；人工依据只允许人工消息，不能因恢复助手而授权自动回复。
- 普通入站处理同步调整为原子提交：核验来源、规则处理、权限、事件、队列及 inbox 结果一起提交，避免首条 FAQ 在核验结果尚未落库时被误拦。
- 来源被删除、过期或墓碑标记后失效关闭。旧库无来源的窗口不得猜造证据；保留历史并停止授权。可信 START 仅恢复此前已建立、仍有效的依据，不延长截止、不复活已取消队列。

**回归与验收：** `Are you insured?` → handoff → 人工确认 → 窗口内人工回复；未经确认、错误来源、未核验、过期、STOP、21610、来源被删除均拒绝。第 23 小时审核不会获得新的 24 小时；新咨询不会续期旧队列；任一步失败不留下孤立权限或队列。营销同意保持不变。

**风险：** 内容是否属于服务咨询依赖人工判断；系统只提供明确操作和审计，不能宣称自动验证自由文本语义。

### P1：⑤ 增加显式正式入站策略

**范围：** config、outbox、engine、app、前端和配置示例。

- 新增 `RECIPIENT_POLICY=test_allowlist|inbound_service`，默认测试策略。测试策略继续强制白名单；正式策略只允许有可靠来源、有效窗口和适格依据的 `service_reply`。
- 正式批准使用独立的 `INBOUND_SERVICE_APPROVAL_RECORDED`，不继承测试批准。策略仅由服务器配置开启，UI 只展示状态。
- 两种策略均保留 STOP、运营商阻断、接管、停发、紧急停止、恢复审查、分段及分钟/日限额。

**回归与验收：** 测试模式取消非白名单任务；正式模式允许合格新客向假 provider 提交；随意填写号码、缺来源、营销和 missed-call 外发均拒绝。所有停发与限额继续有效。

**风险：** 正式策略扩大费用暴露；代码实现和离线验收不等于授权真实开启，应用限额也不是账单硬上限。

### P1：④ 关闭已提交预约草稿

**范围：** engine、增量迁移及预约回归测试。

- 保存待人工确认请求后关闭并清空活动草稿；下一请求重新收集服务、地点、时间、联系方式。明确的新请求及过期草稿同样重新开始。
- 正常未完成多轮草稿继续填写；移除跨会话按相同四字段复用旧请求，重复事件仍由事件 ID 去重。
- 迁移关闭旧库已提交的完整草稿；无法证明仍有效的旧草稿不作为新请求默认值。保留预约历史，不增加预约确认或日历功能。

**回归与验收：** 第一请求提交后，新服务请求必须重新询问缺失字段；独立新请求即使详情相同也可新增 pending；重复同一事件只留一条。多轮续填正常，全部请求仍待人工确认。

**风险：** 草稿关闭与事件结果必须同事务提交，避免重试重复建单或误清当前草稿。

### P2：③ 区分预约规则问句与预约提交

**范围：** model、engine 及 FAQ/预约回归测试。

- “How do I book?” 等规则咨询进入 `requests` FAQ，输出批准答案，不创建草稿或预约。
- “I want to book…” 等明确请求进入收集流程；模糊或混合意图转人工。保留五个主题、最多五条及批准要求。

**回归与验收：** 第五答案实际出现在回复中且无预约副作用；未批准时 handoff；明确预约继续正常多轮收集。

**风险：** 确定性规则仍有语言覆盖限制，无法判定时不猜测提交意图。

### P2：⑦ 统一当前销售、交付与运维范围

**范围：** README、SERVICE_SCOPE_REVIEW、PLATFORM_DRAFTS、[REAL_E2E_PLAN](<D:/SMS Reception Assistant/docs/REAL_E2E_PLAN.md>)；同步启动、部署、运维、客户验收清单和测试报告的受影响表述。

- 清除当前可复制销售文案中的 15/30 FAQ、旧套餐和“真实联调另报价”。真实测试属于约定交付，具体外部行动仍需授权；缺少前置条件时记录未完成，不宣称已经交付真实验证。
- 明确持续维护需另定协议。交付方负责操作说明、演练及测试临时材料的清理交接；客户负责持续备份、访问控制/加密、保留期调度、旧备份和 provider 数据清理、监控及费用。必要退订/去重记录不能被误称为全部清除。

**回归与验收：** 四份主文档逐项一致，无旧报价或范围残留；已实现功能、待修复内容、历史证据和未执行真实测试准确区分。

**风险：** 既不能用旧套餐缩小新范围，也不能因包含真实测试而保证注册批准、运营商送达或生产运营。

## 3. 回归路径与验收顺序

主要测试范围为现有 engine、outbox、service pipeline、service HTTP、provider 和 operations 测试；补充有业务意义的并发、权限、迁移和异常输入场景。服务测试准备持久化假 provider 核验来源，不增加“测试专用权限绕过”。

1. **Windows 开发回归：** Python/SQLite 业务、线程协调、模拟 provider、本地 HTTP 和认证回归。POSIX 锁、权限、符号链接和运维路径单独分类；不伪造通过，也不将平台错误混作业务失败。
2. **Linux 完整离线回归：** 使用用户指定、已授权且具备依赖的 Linux 环境运行原测试和新增测试，验证真实进程排他、WAL 备份、恢复门禁、抑制/去重/用量保留、删除与保留期。缺少该环境时明确完整验收尚未完成；不安装 WSL/Docker 或修改系统。
3. **登录后核心 UI：** 使用隔离空库、发送关闭和模拟入站，实际验证五 FAQ、未知咨询人工确认/回复、接管/恢复、第二次预约、队列取消、日志、登录退出及异常提示，关联浏览器行为与数据库/假 provider 证据。
4. **迁移与恢复：** 验证旧库重复升级幂等、历史保留、无来源权限失效、旧队列不被新窗口复活，以及恢复后继续暂停和审查。

证据归属必须分开：历史独立 Windows 结果为 **218项：197通过、1失败、20出错、0跳过**；原 [TEST_REPORT](<D:/SMS Reception Assistant/docs/TEST_REPORT.md:29>) 的 Linux 通过记录属于原运行。已有正常 UI 证据仍有效，但不能替代修复后验收。**本轮没有新测试统计。**

## 4. 批准与真实 E2E 边界

本计划批准后，仅实施上述本地增量修复、迁移、文档和离线/UI 验收；保留现有 Python + SQLite 项目，不重写，不扩展 LLM、语音、CRM、日历或多租户。

真实 E2E 当前仍未执行，安排在完整离线回归与核心 UI 验收之后。执行前另行提交并取得批准：客户号码与注册资格、参与者和权限、精确正文、方向与条数、分段、日期窗口、当前费用/币种/预算、停止条件及清理责任。受控 E2E 使用测试白名单，并分别记录 API 接受、状态回调和手机实际收到的证据。

实施批准不包含凭据配置、购买/注册、公网开放、真实发送、部署或发布授权。最终报告如实列明通过、失败、阻塞和未执行事项，不声称 production-ready。
